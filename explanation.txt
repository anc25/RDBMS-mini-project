1. PROJECT OVERVIEW
=====================================================================

THE PROBLEM

On a campus people lose things (phones, wallets, ID cards, keys) and
other people find those things. Today there is no single system to
connect them. The finder hands it to some office, the owner registers
a complaint somewhere else, and nobody runs the matching by hand.

THE APP

Campus Lost and Found is a web application where:

  - a student or staff member reports a LOST item,
  - another person reports a FOUND item,
  - the database scores and suggests MATCHES between them,
  - the owner of the lost item submits a CLAIM (with proof) on the
    found item it believes is theirs,
  - an ADMIN reviews the claim and VERIFIES or REJECTS it,
  - verification automatically updates the item, the report, the other
    pending claims, and records a HANDOVER,
  - everything important is written to an AUDIT LOG by triggers.

WHO THE USERS ARE

  - user (student or staff): register, log in, report lost items,
    report found items, browse found items, see matches for their own
    reports, submit claims, track their own claims.
  - admin: everything above, plus review the claim queue (verify or
    reject with a note), see statistics, and read the audit log.

THE FULL WORKFLOW IN ONE LINE

  lost report -> found item -> match (scored) -> claim -> admin verify
  -> item claimed + report resolved + handover recorded -> audit log.

ONE WORKED EXAMPLE (uses real seed data)

  Anchal Singh (user_id 2, email user@test.com) loses a black iPhone.
  On 6 days ago (relative to today) the seed inserts this row
  (sql/mysql/seed.sql):

    (1, 2, 1, 1, 'Black iPhone 13',
     'Black iPhone with a blue silicone case, cat photo as lock screen',
     CURDATE() - INTERVAL 6 DAY, NOW() - INTERVAL 6 DAY)

  category_id 1 is "Phone" (see the 9 categories in the seed) and
  location_id 1 is "Library". Status defaults to 'open'.

  Rohan Mehta (user_id 3) finds a phone in the Library and hands it
  in. The seed's found row is:

    (1, 3, 1, 1, 'Black iPhone',
     'Black iPhone with a blue case, found near the reading hall',
     CURDATE() - INTERVAL 5 DAY, 'Library help desk',
     NOW() - INTERVAL 5 DAY)

  The stored procedure sp_find_matches runs for report 1 and scores
  found item 1:
    same category (Phone)        +40
    same location (Library)      +30
    found 5 days ago, lost 6 days
    ago -> within the 7-day
    window                      +20
    first word "Black" appears in
    the found title "Black
    iPhone"                     +10
                                ---- total 100 (only rows with 50+)
  A match row is saved and the report status becomes 'matched'.

  Anchal opens the item page, writes proof ("Lock screen is a photo of
  my cat and the case is blue" - this is the real seed proof text of
  claim 1), and submits a claim. The claim triggers set the item to
  'claim_pending'. In the current seed claim 1 stays PENDING - it is
  one of the four pending claims, so an examiner can watch the admin
  verify it live during the demo.

  The admin (admin@test.com) opens the admin page, checks the proof,
  and verifies. The sp_verify_claim transaction then: marks the claim
  verified, sets item 1 to 'claimed', sets report 1 to 'resolved',
  rejects every other pending claim on the item with the note "Another
  claim was verified for this item", and inserts a Handover row.
  Triggers write audit log rows at every step. The item is handed
  back - workflow complete.

3. TWO DATABASE VERSIONS
=====================================================================

WHY TWO VERSIONS EXIST

  TiDB (the cloud database we plan to host the app on) is
  MySQL-compatible for tables and queries, but it DOES NOT support
  triggers, stored procedures, events or user-defined functions
  (documented at the top of sql/tidb/APP_LOGIC.md). The project's
  core showcase IS triggers and procedures. So the team split the
  SQL in two:

  sql/mysql/ - THE FULL VERSION (for the local run, the report and
               the viva)
    schema.sql   the 8 tables and every constraint (unchanged)
    logic.sql    the 10 triggers, the 2 procedures, the 2 views
    seed.sql     the demo data; triggers and CALLs do the work while
                 it loads
    reset.sql    DROP DATABASE + rebuild + SOURCE the other three

  sql/tidb/ - THE TIDB CLOUD VERSION (no triggers, no procedures)
    Same tables, same constraints, same data. Each file does one job
    (listed in section 2), loaded in numerical order 00 -> 04
    (see README "Host the database on TiDB Cloud"):
      00 creates the database (also done inside 01; 00 exists for the
         web console path where you want an explicit first step),
      01 creates the tables and constraints and the lookup rows,
      02 creates the views,
      03 seeds all demo data writing the trigger/procedure effects as
         plain SQL (audit rows, status flips, matches, handovers),
      04 prints counts that must be: Users 10, LostReports 20,
         FoundItems 20, Matches 28, Claims 9 (3 verified, 2 rejected,
         4 pending), Handovers 3, AuditLog 57; claimed items 3,
         claim_pending 3, unclaimed 14.

EXACTLY WHAT THE TIDB VERSION KEEPS AND DROPS
(based on sql/tidb/01_schema.sql, not assumptions)

  KEEPS (all enforced by TiDB itself):
    - all 8 tables with the same columns and types
    - PRIMARY KEY with AUTO_INCREMENT (note from the file comment: on
      a distributed cluster ids may be unique but not consecutive -
      they can jump)
    - all FOREIGN KEYs with all three ON DELETE actions
      (RESTRICT for users/categories/locations/claims/handovers,
      CASCADE for Matches, SET NULL for Claims.report_id and
      Claims.reviewed_by)
    - UNIQUE constraints: Users.email, Matches (report_id, item_id),
      Handovers.claim_id
    - CHECK constraints: CHAR_LENGTH(title) >= 3 (twice) and
      score BETWEEN 0 AND 100
    - ENUM columns: roles and all status columns
    - DEFAULTs: CURRENT_TIMESTAMP and the starting statuses
    - views (02_views.sql is identical to the MySQL version)
    - transactions: TiDB supports pessimistic transactions, so
      SELECT ... FOR UPDATE row locks work (APP_LOGIC's last section)

  DROPS (edited out of the TiDB schema, impossible on TiDB):
    - all 10 trg_* triggers  -> rules move into the app (mapping
      table below)
    - sp_find_matches and sp_verify_claim
    - so also: automatic audit logging, automatic item status flips,
      automatic future-date rejection - none of these happen inside
      the database anymore.

  The team should demo the MySQL version in the viva, because it is
  the version where the database visibly does the interesting work
  (see the new viva questions in section 15).


SIDE-BY-SIDE MAPPING: MYSQL OBJECT -> TiDB / APP EQUIVALENT
(quotes are copied from sql/tidb/APP_LOGIC.md; section numbers in
brackets are the APP_LOGIC headings)

TRG_LOST_BEFORE_INSERT / TRG_FOUND_BEFORE_INSERT ["date cannot
be in the future"]  (APP_LOGIC 1)

  MySQL: the trigger aborts the insert with
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
    'Date lost cannot be in the future';   (and the found variant)

  TiDB/app (quoted):

    SELECT (DATE(?) > CURDATE()) AS invalid;

  plus the note the file gives: app-side check in JavaScript
  ("if (dateLost > todayISO()) return 400"). Difference: the rule is
  enforced by our route handler before it even inserts. It is no
  longer automatic - another client could still insert a future date;
  the database will accept it.

TRG_LOST_AFTER_INSERT / TRG_FOUND_AFTER_INSERT
["audit rows on new reports/items"]  (APP_LOGIC 2)

  MySQL: trigger inserts the AuditLog row for every new report/item.

  TiDB/app (quoted):

    INSERT INTO LostReports (...) VALUES (...);
    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('LostReports', 'INSERT', LAST_INSERT_ID(), ?);

  Difference: two statements run together in one transaction;
  LAST_INSERT_ID() takes the place of the trigger's NEW.report_id.
  If the app forgets the second statement, history is simply missing.

TRG_CLAIM_BEFORE_INSERT ["the claim business rules"] (APP_LOGIC 3)

  MySQL: one trigger with four rules and four exact messages.

  TiDB/app (quoted):

    SELECT status, finder_id INTO @status, @finder
    FROM FoundItems WHERE item_id = ?;
    -- @status IN ('claimed','disposed')
    --    -> 'This item is no longer available to claim'
    -- @finder = claimant
    --    -> 'You cannot claim an item you found yourself'

    SELECT COUNT(*) FROM Claims
    WHERE item_id = ? AND claimant_id = ? AND status = 'pending';
    -- count > 0
    --    -> 'You already have a pending claim on this item'

    SELECT user_id FROM LostReports WHERE report_id = ?;
    -- owner <> claimant
    --    -> 'The linked lost report does not belong to you'

  Difference: the route runs the checks, reads the results and raises
  HTTP 409 with the same texts (as the file instructs). Race note:
  between the check and the INSERT another claim could sneak in,
  because no trigger is watching - the transaction plus care
  minimises it.

TRG_CLAIM_AFTER_INSERT ["item becomes claim_pending + audit row"]
(APP_LOGIC 4)

  TiDB/app (quoted):

    INSERT INTO Claims (...) VALUES (...);
    UPDATE FoundItems SET status = 'claim_pending'
    WHERE item_id = ? AND status = 'unclaimed';
    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('Claims', 'INSERT', LAST_INSERT_ID(), ?);

  Identical effects, but the three-statement sequence is OUR job.

TRG_CLAIM_BEFORE_UPDATE / TRG_CLAIM_AFTER_UPDATE
["no double review, one verified claim per item, status sync"]
(APP_LOGIC 5)

  TiDB/app (quoted):

    -- reviewed claims cannot change again
    SELECT status FROM Claims WHERE claim_id = ? FOR UPDATE;
    -- status <> 'pending'
    --    -> 'This claim has already been reviewed'

    -- only one verified claim per item
    SELECT COUNT(*) FROM Claims
    WHERE item_id = ? AND status = 'verified' AND claim_id <> ?;
    -- count > 0
    --    -> 'Another claim is already verified for this item'

    -- the actual verify + sync (one transaction)
    UPDATE Claims SET status = 'verified', reviewed_by = ?,
           admin_note = ?, reviewed_at = NOW()
    WHERE claim_id = ?;
    UPDATE FoundItems SET status = 'claimed'   WHERE item_id = ?;
    UPDATE LostReports SET status = 'resolved' WHERE report_id = ?;
    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('Claims', 'STATUS_CHANGE', ?, ?);

  And rejecting a claim ("sync in the other direction", quoted):

    UPDATE Claims SET status = 'rejected', reviewed_by = ?,
           admin_note = ?, reviewed_at = NOW()
    WHERE claim_id = ?;
    -- flip the item back only if no other pending claim remains
    UPDATE FoundItems SET status = 'unclaimed'
    WHERE item_id = ? AND status = 'claim_pending'
      AND NOT EXISTS (SELECT 1 FROM Claims
                      WHERE item_id = ? AND status = 'pending');

  The FOR UPDATE is what replaces the automatic trigger protection ?
  it locks the row for the critical section. The NOT EXISTS guard
  copies the trigger's "no other pending claims remain" rule into one
  UPDATE.

SP_FIND_MATCHES(report_id)  (APP_LOGIC 6)

  TiDB/app (quoted):

    INSERT IGNORE INTO Matches (report_id, item_id, score)
    SELECT s.report_id, s.item_id, s.score
    FROM (
      SELECT r.report_id, f.item_id,
        (CASE WHEN f.category_id = r.category_id THEN 40 ELSE 0 END)
      + (CASE WHEN f.location_id  = r.location_id THEN 30 ELSE 0 END)
      + (CASE WHEN f.date_found BETWEEN r.date_lost
                   AND DATE_ADD(r.date_lost, INTERVAL 7 DAY)
               THEN 20 ELSE 0 END)
      + (CASE WHEN CHAR_LENGTH(SUBSTRING_INDEX(r.title, ' ', 1)) >= 3
              AND LOCATE(LOWER(SUBSTRING_INDEX(r.title, ' ', 1)),
                         LOWER(f.title)) > 0
             THEN 10 ELSE 0 END) AS score
      FROM LostReports r
      JOIN FoundItems f ON f.status IN ('unclaimed', 'claim_pending')
      WHERE r.report_id = ? AND r.status IN ('open', 'matched')
        AND f.category_id = r.category_id
    ) AS s
    WHERE s.score >= 50;

    UPDATE LostReports SET status = 'matched'
    WHERE report_id = ? AND status = 'open' AND ROW_COUNT() > 0;
    -- (run ROW_COUNT() right after the INSERT IGNORE,
    --  then this UPDATE)

  Difference: the body of the procedure becomes one big statement the
  route runs; ROW_COUNT() (rows changed by the last statement) takes
  the place of the procedure's variable. The identical statement is
  also in sql/tidb/03_seed.sql, which is how the seeded Matches were
  produced without the procedure - but the seed's UPDATE ... WHERE
  report_id IN (SELECT report_id FROM Matches) does the flip for all
  matching reports at once instead of per report.

SP_VERIFY_CLAIM(claim_id, admin_id, note, remarks)  (APP_LOGIC 7)

  TiDB/app (quoted):

    START TRANSACTION;

    -- admin check first
    SELECT COUNT(*) FROM Users WHERE user_id = ? AND role = 'admin';
    -- count = 0 -> 'Only an admin can verify a claim'

    SELECT item_id FROM Claims
    WHERE claim_id = ? AND status = 'pending' FOR UPDATE;
    -- null -> 'Claim not found or already reviewed'

    UPDATE Claims SET status = 'verified', reviewed_by = ?,
           admin_note = ?, reviewed_at = NOW()
    WHERE claim_id = ?;

    UPDATE Claims SET status = 'rejected', reviewed_by = ?,
           admin_note = 'Another claim was verified for this item',
           reviewed_at = NOW()
    WHERE item_id = ? AND claim_id <> ? AND status = 'pending';

    UPDATE FoundItems SET status = 'claimed'   WHERE item_id = ?;
    UPDATE LostReports SET status = 'resolved' WHERE report_id = ?;

    INSERT INTO Handovers (claim_id, handed_by, remarks)
    VALUES (?, ?, ?);
    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('Claims', 'STATUS_CHANGE', ?, ?);

    COMMIT;

  Difference: same steps, but the procedure's automatic triggers and
  exit handler are gone; the route handler wraps this in a MySQL
  pool.getConnection() + beginTransaction() and rolls back on any
  thrown error (the file's own wording: TiDB's pessimistic
  transactions make the FOR UPDATE row lock behave like MySQL's).

TRG_HANDOVER_* (where did the handover trigger land?)

  APP_LOGIC 7 covers the whole verify script, so the handover INSERT
  happens inside the transaction AFTER the claim was verified by the
  FOR UPDATE + UPDATE steps - the "only for a verified claim"
  guarantee comes from the ORDER of the statements rather than from
  the trg_handover_before_insert rule. Honest gaps to be aware of:
    - the flattened script shows no AuditLog row for the Handovers
      table itself, while THE MYSQL VERSION writes that
      (trg_handover_after_insert); the current mock store DOES write
      one. [GAP in APP_LOGIC - worth mentioning openly in the viva]
    - if app code ever ran the handover INSERT outside this script,
      nothing in a TiDB database would stop it for an unverified
      claim.

HOW THE MOCK STORE FITS IN

  Today the app runs mock (lib/mock-store.js), and the mock helpers
  already implement exactly these rules in JavaScript (same messages).
  So the TiDB conversion plan is: keep the mock logic LOCALLY, change
  each rule from manipulating arrays into executing the quoted SQL -
  the app layer does not move, only its insides do.

4. TECH STACK AND WHY
=====================================================================

  NEXT.JS (APP ROUTER, PLAIN JAVASCRIPT)
  One project holds the pages AND the API (route handlers in app/api).
  No build step between frontend and backend, same origin (no CORS
  problems), and one language. Plain JavaScript because the team does
  not need TypeScript; the viva is easier to explain without types.

  BUN
  The package manager and script runner (bun add, bun run dev). One
  tool, fast installs, one lockfile (bun.lock). It avoids npm/yarn
  lockfile conflicts between the two team members.

  MYSQL 8 (LOCAL) AND TIDB CLOUD (CLOUD OPTION)
  MySQL 8 comes from college labs and supports triggers, stored
  procedures, views and CHECK constraints - everything the project
  must demonstrate. TiDB is a MySQL-compatible distributed database
  whose free tier can host the data in the cloud - the price is that
  it cannot run the triggers/procedures (section 3).

  MYSQL2 DRIVER WITH RAW SQL (NO ORM)
  mysql2 is the MySQL (and TiDB) driver for JavaScript. Raw SQL means
  every query is written by hand and the examiner can see each one.
  An ORM would hide the SQL behind method calls - this project is
  graded on the SQL, so the SQL should be visible.
  [MOCK ONLY as of this writing - mysql2 is not installed yet]

  BCRYPTJS
  A pure-JavaScript password hashing library. Passwords must never be
  stored as plain text; bcrypt makes a one-way salted hash. The seed
  already stores $2b$ hashes that bcryptjs can verify. (Not used by
  the running app yet because auth is mock.)  [MOCK ONLY]

  IRON-SESSION
  A tiny library for a signed, encrypted, httpOnly session cookie.
  (Referenced in the PRD; the mock app uses a plain httpOnly cookie.)
  [MOCK ONLY]

  BOOTSTRAP 5.3 (CSS FROM CDN)
  Fast, clean, familiar layout. Loaded as a CSS-only stylesheet link;
  the app does NOT load Bootstrap's JavaScript, so modals, tabs,
  toasts and collapsible rows are built with React state, and light /
  dark mode uses Bootstrap's own data-bs-theme attribute set on the
  html element (components/ThemeToggle.js).

5. HOW THE APP IS STRUCTURED
=====================================================================

ARCHITECTURE IN ONE DIAGRAM

  +---------------------+
  |   Browser pages     |   app/*/page.js  ("use client")
  |   (React components)|   components/*.js
  +----------+----------+
             |  every request goes through one file:
             v
  +---------------------+
  |      lib/api.js     |   one function per endpoint, throws
  |   (all fetch calls) |   Error(data.error) on non-2xx responses
  +----------+----------+
             |  fetch("/api/...", { credentials: "same-origin" })
             v
  +---------------------+
  |  Route handlers     |   app/api/.../route.js
  |   (Next.js backend) |
  +----------+----------+
             |  MOCK NOW: helper calls into lib/mock-store.js
             |  REAL LATER: mysql2 runs the SQL documented in
             |             sql/tidb/APP_LOGIC.md (or the triggers
             |             fire themselves on sql/mysql/)
             v
  +---------------------+          +---------------------+
  |   MySQL 8 local     |   or     |   TiDB Cloud        |
  |   triggers + procs  |          |   tables + views    |
  +---------------------+          +---------------------+

MOCK-FIRST: HOW IT WORKS RIGHT NOW

  lib/mock-store.js holds the fake database in memory. It mirrors
  sql/mysql/seed.sql exactly (10 users, 9 categories, 8 locations,
  20 lost reports, 20 found items, 9 claims, 57 audit rows, 28 match
  rows computed by the same scoring formula) and re-implements the
  same rules the MySQL triggers enforce, including the same error
  messages. The store lives on globalThis so Next.js hot reloads do
  not wipe it during a demo.

  Every route handler is deliberately thin: it checks who the user is
  (lib/mock-auth.js reads an httpOnly cookie), calls one helper
  function from mock-store, and returns JSON. So replacing a handler's
  body with real SQL does not change anything else.

HOW A ROUTE IS SWITCHED FROM MOCK TO REAL (the plan, not done yet)
  [NOT BUILT YET]

  1. open the route file, e.g. app/api/found/[id]/route.js
  2. replace the mock-store call inside the handler body with a mysql2
     query using the lib/db.js pool and ? placeholders
     (against MySQL OR TiDB - the connection string decides which)
  3. keep the EXACT response shape (the snake_case field names) and
     the same HTTP status codes; the frontend already expects them
  4. delete that handler's now-unused helper from mock-store.js
  5. repeat in the order: auth -> found/lost -> claims -> admin.

  lib/mock-auth.js is a single small file on purpose: it holds all the
  cookie logic so it can be replaced wholesale by iron-session.

WHAT EACH PAGE SHOWS

  /                  login and register tabs; on success -> /dashboard
  /dashboard         "Hello, <name>", three action cards, counters
                     (my open reports, my pending claims, matches
                     found) and the five best recent matches
  /report-lost       title, category, location, date (max = today),
                     description; creates the report and runs matching
  /report-found      same plus "currently stored at"; item becomes
                     unclaimed
  /browse            keyword / category / location / date range filters
                     over unclaimed found items (the view
                     v_open_found_items in real mode)
  /item/[id]         full item details and the claim form (proof text
                     + optional link to one of my open lost reports);
                     if the item is not unclaimed or claim_pending the
                     form is disabled and a badge is shown instead
  /my-reports        reports with status badges; expanding a row shows
                     its matches (score as a progress bar)
  /my-claims         claims with status badges and the admin note
  /admin             claim queue (pending claims, verify/reject with a
                     note in a modal), stats (counters, hotspot
                     locations, category counts, items unclaimed over
                     30 days), audit log table

PAGE GUARDS

  Every page except / wraps itself in components/AuthGuard.js, which

NORMALIZATION UP TO 3NF

  1NF (first normal form): every column holds one simple value, rows
  are unique (primary keys). Names are not stored as lists.

  2NF (second normal form): every column depends on the WHOLE key.
  Each table has a single-column key, so this holds.

  3NF (third normal form): no column depends on another non-key
  column. This is why Categories and Locations are separate tables:

    - if LostReports stored "Phone" as text and the category were
      later renamed to "Mobile Phone", every old row would still say
      "Phone" (update anomaly).
    - a new report could spell it "phone", "Phone", "PHONE" and counts
      per category would split (insertion inconsistency).
    - deleting the last report of a category would also delete the
      knowledge that the category exists (deletion anomaly).

  With a category_id foreign key the name lives in ONE place
  (Categories) and reports reference it. Same reasoning forLocations.

  Why Matches is its own table: the relationship user-reported-lost vs
  user-found-item carries its own attribute (score) and its own rules
  (a report can have many matches; the same pair must appear once).
  That is a textbook many-to-many with attributes -> junction table.

  Why Claims is its own table: a claim is not just an update to an
  item - it has its own life (proof, status, review). An item can have
  SEVERAL claims (competing), one of which is verified.


CONSTRAINT TYPES USED, WITH ONE EXAMPLE EACH

  PRIMARY KEY      the row identifier. Example: Users.user_id
                   INT AUTO_INCREMENT PRIMARY KEY.
  FOREIGN KEY      a reference that must exist. Example:
                   fk_lost_user (user_id -> Users).
  ON DELETE RESTRICT  deleting the parent is refused while children
                   exist. Example: you cannot delete a User who still
                   has lost reports - history is protected.
  ON DELETE CASCADE  deleting the parent deletes the children.
                   Example: deleting a LostReport deletes its Matches
                   rows - matches of a deleted report are meaningless.
  ON DELETE SET NULL  deleting the parent nulls the child column.
                   Example: deleting a report linked to a claim sets
                   Claims.report_id to NULL - the claim itself must
                   survive, only the optional link disappears.
  UNIQUE           no duplicates. Users.email (two accounts cannot
                   share an email), Matches (report_id, item_id), and
                   Handovers claim_id (one handover per claim).
  NOT NULL         the value is required. Example: title, date_lost,
                   status on LostReports.
  CHECK            an arbitrary condition. Examples:
                   CHECK (CHAR_LENGTH(title) >= 3) and
                   CHECK (score BETWEEN 0 AND 100).
  ENUM             closed list of strings. Example: LostReports.status
                   must be open / matched / resolved / closed.
  DEFAULT          value assigned when not given. Example:
                   status DEFAULT 'open',
                   created_at DEFAULT CURRENT_TIMESTAMP.

7. TRIGGERS
=====================================================================

(Applies to the sql/mysql/ version. On TiDB nothing below exists -
section 3's mapping table shows where each rule went.)

A TRIGGER is code the database runs automatically (BEFORE or AFTER an
INSERT, UPDATE or DELETE on one table) for every affected row. Nobody
calls it; it fires. We use triggers so the RULES live next to the
data: even a student typing SQL by hand in a mysql terminal cannot
break them. This is the "why": application code can be bypassed; the
database cannot.

SIGNAL SQLSTATE '45000'

  SIGNAL is how a trigger or procedure ABORTS with a custom error.
  SQLSTATE 45000 is the reserved class for user-defined errors. The
  full pattern is:

    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '<message>';

  The message travels to the client as the error's sqlMessage. The app
  catches it and turns it into an HTTP 409 response with that exact
  text.

WHY THE DATE CHECKS ARE TRIGGERS AND NOT CHECK CONSTRAINTS

  MySQL does not allow non-deterministic functions like CURDATE()
  inside a CHECK constraint, so the "no future dates" rule needs a
  BEFORE INSERT trigger instead.

THE 10 TRIGGERS OF sql/mysql/logic.sql

---------------------------------------------------------------
1. trg_lost_before_insert  -  LostReports, BEFORE INSERT
---------------------------------------------------------------

  CREATE TRIGGER trg_lost_before_insert BEFORE INSERT ON LostReports
  FOR EACH ROW
  BEGIN
    IF NEW.date_lost > CURDATE() THEN
      SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
        'Date lost cannot be in the future';
    END IF;
  END

  NEW is the row being inserted. If the date is in the future, stop.
  Example: a user picks tomorrow's date in the form. The insert dies
  and the user sees the message above (HTTP 409 in the app).

---------------------------------------------------------------
2. trg_found_before_insert  -  FoundItems, BEFORE INSERT
---------------------------------------------------------------

  Same pattern on FoundItems with
    'Date found cannot be in the future'.

---------------------------------------------------------------
3. trg_lost_after_insert  -  LostReports, AFTER INSERT
---------------------------------------------------------------

  CREATE TRIGGER trg_lost_after_insert AFTER INSERT ON LostReports
  FOR EACH ROW
  BEGIN
    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('LostReports', 'INSERT', NEW.report_id,
            CONCAT('Lost report "', NEW.title, '" filed by user ',
            NEW.user_id));
  END

  It runs after the row exists, so NEW.report_id has its
  AUTO_INCREMENT value, and writes one audit row. Why AFTER (not
  BEFORE): the id of a brand new row exists only after insert.

---------------------------------------------------------------
4. trg_found_after_insert  -  FoundItems, AFTER INSERT
---------------------------------------------------------------

  Same pattern with ('FoundItems', 'INSERT', NEW.item_id,
  'Found item "<title>" reported by user <finder_id>').

---------------------------------------------------------------
5. trg_claim_before_insert  -  Claims, BEFORE INSERT
   (THE BIG ONE)
---------------------------------------------------------------

  DECLAREs local variables, loads the item's current status and
  finder, then applies four rules in order:

    - item already claimed or disposed ->
        SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
        'This item is no longer available to claim'
    - claimant is the finder ->
        'You cannot claim an item you found yourself'
    - the claimant already has a PENDING claim on this item ->
        'You already have a pending claim on this item'
    - the linked lost report exists and is not the claimant's ->
        'The linked lost report does not belong to you'

  Why BEFORE: it can still ABORT the insert. AFTER triggers cannot
  cancel an insert - they only react to one that happened.

---------------------------------------------------------------
6. trg_claim_after_insert  -  Claims, AFTER INSERT
---------------------------------------------------------------

    UPDATE FoundItems SET status = 'claim_pending'
    WHERE item_id = NEW.item_id AND status = 'unclaimed';

    INSERT INTO AuditLog (table_name, action, record_id, details)
    VALUES ('Claims', 'INSERT', NEW.claim_id,
            CONCAT('User ', NEW.claimant_id, ' claimed item ',
            NEW.item_id));

  The moment a claim is submitted, the item becomes claim_pending so
  other users can see it is in play (but a second claim by the same
  user is blocked by trigger 5).

---------------------------------------------------------------
7. trg_claim_before_update  -  Claims, BEFORE UPDATE
---------------------------------------------------------------

  Three rules:
    - already reviewed (pending -> reviewed again) -> block:
        'This claim has already been reviewed'
    - changing to verified while ANOTHER claim on the same item is
      already verified -> block:
        'Another claim is already verified for this item'
    - stamp reviewed_at automatically:
        IF OLD.status = 'pending' AND NEW.status <> 'pending'
        AND NEW.reviewed_at IS NULL THEN SET NEW.reviewed_at = NOW();

---------------------------------------------------------------
8. trg_claim_after_update  -  Claims, AFTER UPDATE
---------------------------------------------------------------

  Keeps statuses in sync when a claim flips state:

    verified  ->  item becomes 'claimed';
                  if the claim links a report, that report becomes
                  'resolved'.
    rejected  ->  if no OTHER pending claim remains on the item, the
                  item goes back to 'unclaimed' (only when its
                  current status is 'claim_pending').

  then writes: AuditLog ('Claims', 'STATUS_CHANGE', claim_id,
  'Claim <id> changed from <old> to <new>').

  Why not a trigger for REJECTING the other pending claims? A trigger
  cannot safely update its OWN table (Claims) inside itself; after
  update row-level triggers modifying other rows of the same table
  causes cascading, undefined behaviour, so that job belongs to the
  stored procedure sp_verify_claim (section 8).

---------------------------------------------------------------
9. trg_handover_before_insert  -  Handovers, BEFORE INSERT
---------------------------------------------------------------

  Reads the claim's status; if it is not 'verified':
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
    'A handover can only be recorded for a verified claim'
  This single rule is what makes "handover cannot be recorded for an
  unverified claim" a database guarantee.

---------------------------------------------------------------
10. trg_handover_after_insert  -  Handovers, AFTER INSERT
---------------------------------------------------------------

  Writes AuditLog ('Handovers', 'INSERT', handover_id,
  'Item handed over for claim <id> by admin <id>').

8. STORED PROCEDURES AND THE TRANSACTION
=====================================================================

(MySQL version, sql/mysql/logic.sql. On TiDB: section 3.)

A STORED PROCEDURE is a saved SQL program stored in the database and
called with CALL. It can take parameters and run many statements.

---------------------------------------------------------------
sp_find_matches(IN p_report_id INT)
---------------------------------------------------------------

  The scoring engine. Called once when a lost report is created (the
  report route runs matching on creation - FR4) and again by the
  "Re-run matching" button on /my-reports.

  What it considers: found items whose status is 'unclaimed' or
  'claim_pending', in the SAME CATEGORY as the lost report, while the
  report is still 'open' or 'matched'. (A phone is never a match for
  a wallet - categories must agree.)

  The score (exactly as in sql/mysql/logic.sql):

    (CASE WHEN f.category_id = r.category_id THEN 40 ELSE 0 END)
  + (CASE WHEN f.location_id = r.location_id THEN 30 ELSE 0 END)
  + (CASE WHEN f.date_found
          BETWEEN r.date_lost AND DATE_ADD(r.date_lost, INTERVAL 7 DAY)
          THEN 20 ELSE 0 END)
  + (CASE WHEN CHAR_LENGTH(SUBSTRING_INDEX(r.title, ' ', 1)) >= 3
          AND LOCATE(LOWER(SUBSTRING_INDEX(r.title, ' ', 1)),
                     LOWER(f.title)) > 0
         THEN 10 ELSE 0 END)

  Line by line:
    - +40 same category (always true here, since other categories are
      filtered out already - the constant 40 says "category match is
      the base requirement").
    - +30 same location where lost/found.
    - +20 the found date lies in the 7 days AFTER the loss date
      (BETWEEN is inclusive on both ends).
    - +10 the first word of the lost title (with length >= 3 so short
      words like "HP" do not fire everywhere) appears anywhere in the
      found title, case-insensitively (LOCATE on LOWER).

  INSERT IGNORE skips existing (report_id, item_id) pairs - the
  UNIQUE(report_id, item_id) constraint makes re-runs safe.

  Only rows with score >= 50 are inserted.

  If any new row was created, an open report becomes 'matched'.

  It returns ONE ROW:
    SELECT v_created AS matches_created;

  WORKED EXAMPLE (verified against the actual seed results):
  report 1 = 'Black iPhone 13', category 1 Phone, location 1 Library,
  lost 6 days ago.
    item 1  'Black iPhone',  Phone, Library, found 5d ago:
            40 + 30 + 20 + ("black" in "black iphone" -> 10) = 100
    item 11 'Redmi phone',   Phone, Mess,    found 2d ago:
            40 + 0 + 20 + 0 = 60
    item 13 'Samsung phone', Phone, Library, found 4d ago:
            40 + 30 + 20 + 0 = 90
    item 12 is 'Other' category -> skipped entirely.
  All three (100, 60, 90) beat the 50 cut-off, so all three become
  matches, and report 1's status becomes 'matched'. Across all 20
  reports the seed produces exactly 28 match rows (the sanity check
  file expects Matches 28), spread over 18 matched reports.

  HOW THE APP USES IT: POST /api/lost (create report) calls matching
  immediately; POST /api/lost/[id]/rematch re-runs it and reports
  matches_created to the UI as a toast. GET /api/lost/[id]/matches
  returns ordered matches (best score first) for the expanded row.
  [MOCK ONLY]

---------------------------------------------------------------
sp_verify_claim(p_claim_id INT, p_admin_id INT,
                p_note VARCHAR(255), p_remarks VARCHAR(255))
---------------------------------------------------------------

  The "verify and hand over" step, done as ONE transaction. From
  sql/mysql/logic.sql, the essential steps:

    DECLARE EXIT HANDLER FOR SQLEXCEPTION
    BEGIN
      ROLLBACK;
      RESIGNAL;
    END;

    IF NOT EXISTS (SELECT 1 FROM Users
                   WHERE user_id = p_admin_id AND role = 'admin') THEN
      SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
        'Only an admin can verify a claim';
    END IF;

    START TRANSACTION;

    SELECT item_id INTO v_item FROM Claims
    WHERE claim_id = p_claim_id AND status = 'pending'
    FOR UPDATE;

    IF v_item IS NULL THEN
      SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT =
        'Claim not found or already reviewed';
    END IF;

    UPDATE Claims
    SET status = 'verified', reviewed_by = p_admin_id,
        admin_note = p_note
    WHERE claim_id = p_claim_id;

    UPDATE Claims
    SET status = 'rejected', reviewed_by = p_admin_id,
        admin_note = 'Another claim was verified for this item'
    WHERE item_id = v_item AND claim_id <> p_claim_id
      AND status = 'pending';

    INSERT INTO Handovers (claim_id, handed_by, remarks)
    VALUES (p_claim_id, p_admin_id, p_remarks);

    COMMIT;

  Step by step:
    1. the exit handler: ON ANY SQL ERROR -> ROLLBACK + RESIGNAL.
    2. admin check before even starting.
    3. SELECT ... FOR UPDATE locks the pending claim's row so two
       admins clicking Verify at the same moment cannot both succeed.
    4. marks the claim verified - THE TRIGGERS 7 AND 8 FIRE HERE
       (one-verified-per-item check, reviewed_at stamp, item ->
       claimed, linked report -> resolved, audit rows).
    5. every OTHER pending claim on the same item is rejected with
       the note "Another claim was verified for this item" (the job a
       trigger cannot do on its own table).
    6. a Handover row records the physical return.
    7. COMMIT makes it permanent.

WHAT IS A TRANSACTION AND WHY HERE

  A transaction is a group of statements that either ALL happen or
  NONE happen.

  ACID, with this project as the example:

    A - ATOMICITY: all steps succeed together or none do. If the
        Handovers INSERT failed halfway, the ROLLBACK undoes the
        verified status, the item change and the other rejections -
        the database never shows a half-verified claim. The exit
        handler guarantees this: any SQL error jumps to the handler.

    C - CONSISTENCY: every rule stays true (one verified claim per
        item, item claimed <-> verified claim, handover only for
        verified). Transactions plus triggers enforce them together.

    I - ISOLATION: two admins verifying the same claim at once do not
        interleave; FOR UPDATE + the transaction keeps them serial.

    D - DURABILITY: after COMMIT the data survives a crash (InnoDB
        writes to a transaction log on disk).

  That is also why the procedure, not the route, owns the logic: the
  route (app/api/admin/claims/[id]/verify in real mode) just runs
  CALL sp_verify_claim(?, ?, ?, ?). In mock mode the same behaviour is
  re-implemented in mock-store.js verifyClaim(); on TiDB it becomes
  the flattened transaction quoted in section 3 (APP_LOGIC 7).
  [MOCK ONLY]

A VIEW is a saved SELECT that can be used like a table. It stores no
data itself; it runs its query on use. Views give a stable, simple
name for a complicated join and hide the join from callers. Both
views exist in EXACTLY the same form in sql/mysql/logic.sql and
sql/tidb/02_views.sql. [DONE in both SQL folders; the app does not
read them yet - the routes are mock]  [MOCK ONLY]

v_open_found_items - the list the Browse page shows

  CREATE OR REPLACE VIEW v_open_found_items AS
  SELECT f.item_id, f.title, f.description, f.date_found, f.stored_at,
         f.status, c.name AS category, l.name AS location
  FROM FoundItems f
  JOIN Categories c ON c.category_id = f.category_id
  JOIN Locations  l ON l.location_id = f.location_id
  WHERE f.status = 'unclaimed';

  Purpose: every unclaimed found item with readable category and
  location names. Why useful: the browse/filter route becomes a one
  line SELECT FROM v_open_found_items WHERE ... instead of repeating
  three joins everywhere.

v_claim_details - the admin claim queue

  CREATE OR REPLACE VIEW v_claim_details AS
  SELECT cl.claim_id, cl.status, cl.proof_text, cl.admin_note,
         cl.created_at, cl.reviewed_at,
         u.user_id AS claimant_id, u.name AS claimant_name,
         u.email AS claimant_email,
         f.item_id, f.title AS item_title,
         r.report_id, r.title AS report_title
  FROM Claims cl
  JOIN Users u      ON u.user_id = cl.claimant_id
  JOIN FoundItems f ON f.item_id = cl.item_id
  LEFT JOIN LostReports r ON r.report_id = cl.report_id;

  Purpose: the claim queue row with claimant, item and (optional)
  linked report title. LEFT JOIN with LostReports: report_id may be
  NULL (a claim need not link a report), and a LEFT JOIN keeps the
  row with report_title = NULL in that case; an INNER JOIN would
  hide exactly those claims that the admin must still see.
  [MOCK ONLY - the mock admin route computes the same shape]

12. SECURITY AND ERROR HANDLING
=====================================================================

PASSWORDS
  Never stored plain. bcryptjs hashes each password with a random salt
  (the stored string starts with $2b$10$... - the 10 is the cost
  factor). Login compares with bcrypt.compare. The seeds ALREADY
  store bcrypt hashes, so the swap is ready. In the current mock the
  store keeps plain demo passwords for speed and compares them
  directly - an explicit mock shortcut.  [MOCK ONLY]

PARAMETERIZED QUERIES (AND WHY)
  Every real query must use ? placeholders
  (db.execute('SELECT ... WHERE email = ?', [email])) so values and
  SQL text never mix; passing user input inside a query string is how
  SQL injection happens ("' OR 1=1 --"). The route handlers are
  structured so the swap keeps this rule - no string concatenation of
  input.

SESSION COOKIES
  The session is an httpOnly cookie (JavaScript cannot read it, which
  defeats XSS cookie theft), with sameSite lax. Mock mode stores the
  user id; iron-session will add an encrypted, signed payload. Logout
  clears it.  [MOCK ONLY]

ADMIN-ONLY ROUTES
  Handlers under /api/admin call a guard: no session -> HTTP 401
  {"error":"Not logged in"}; session but role != admin -> HTTP 403
  {"error":"Admin only"}. The UI hides the admin link but the API
  does not trust the UI - the guard is on the server.  [MOCK ONLY]

STATUS CODES AND ERROR MESSAGES
  400 validation (bad email, missing fields, future date)
  401 not logged in
  403 not admin (or not the owner of the record)
  404 the row does not exist
  409 conflict - usually a rule enforced by a trigger in the MySQL
      version, or by an app-side check in the TiDB version. The real
      MySQL mode catches error 1644 (unhandled user-defined
      exception, which is SIGNAL/45000) and returns HTTP 409 with
      {"error": "<the trigger's MESSAGE_TEXT>"} verbatim; the TiDB
      mode raises the same messages itself from the checks quoted in
      section 3.
  All errors are {"error": "message"} JSON; lib/api.js turns any
  non-2xx into a JavaScript Error whose text is shown in a toast, so
  the user always sees WHY something failed.  [MOCK ONLY]

15. VIVA QUESTIONS AND ANSWERS
=====================================================================

Q1. Why is the schema in 3NF?
A. So each fact lives in one place. Categories and Locations are
   separate tables, so a category name is stored once; reports and
   items reference it by id. That removes update, insert and delete
   anomalies (renaming a category updates one row; counts cannot
   split; an unused category still exists).

Q2. What is a foreign key?
A. A column (or set) whose values must match a primary key in another
   table. LostReports.user_id references Users.user_id, so no report
   can belong to a user who does not exist.

Q3. What does ON DELETE CASCADE do, and where do you use it?
A. Deleting the parent row deletes child rows automatically. We use
   it only for Matches: if a lost report is deleted, its matches
   become meaningless, so they go with it.

Q4. Why RESTRICT for users / categories / locations?
A. History must stay intact. You cannot delete a user who has
   reports, or a category in use - the request errors instead of
   silently destroying records.

Q5. What does ON DELETE SET NULL cover?
A. Optional references. Claims.report_id is optional; if its report
   is deleted the claim survives but the link is set to NULL
   (report_id is nullable for this reason).

Q6. What is a trigger?
A. Database code that fires automatically on a row event (BEFORE or
   AFTER INSERT / UPDATE / DELETE). Our claim rules, audit writing
   and status sync are triggers.

Q7. Why put rules in triggers instead of the app?
A. The database is the last line of defence - any client (app,
   Workbench, mysql CLI) gets the same rules. Application checks can
   be forgotten or bypassed; trigger rules cannot.

Q8. Trigger vs stored procedure?
A. A trigger fires automatically on an event; nobody calls it. A
   procedure is saved code you call explicitly (CALL). Our triggers
   enforce single-row rules; sp_find_matches and sp_verify_claim run
   when the app decides to.

Q9. Why does a trigger use SIGNAL '45000'?
A. 45000 is the SQLSTATE class for user-defined errors. SIGNAL makes
   the statement fail with our message; the app maps it to HTTP 409
   with the same text, so the user sees a readable reason.

Q10. Why are future-date checks triggers and not CHECK?
A. MySQL cannot call non-deterministic functions like CURDATE() in a
   CHECK constraint, so a BEFORE INSERT trigger raises the error.

Q11. What is a stored procedure?
A. A stored SQL program in the database, called with CALL. It can
   branch, run transactions, and return a result set.

Q12. What is a transaction? Why does verify need one?
A. A unit of work where all statements commit together or roll back
   together. Verify touches the claim, the item, the linked report,
   the other claims and inserts a handover - if any step fails the
   rest must be undone; otherwise the data would be contradictory.

Q13. What does ACID mean?
A. Atomicity (all or nothing), Consistency (rules stay true),
   Isolation (concurrent runs do not interleave badly; we also use
   SELECT ... FOR UPDATE to lock the claim row), Durability (committed
   data survives crashes).

Q14. What happens if the handover INSERT fails inside
     sp_verify_claim?
A. The exit handler catches the exception, runs ROLLBACK (undoing the
   verify, the item/report status changes and the other rejections)
   and RESIGNALs the error so the route returns 409.

Q15. How do you prevent two verified claims on one item?
A. Two layers: trg_claim_before_update blocks an update to verified
   when another verified claim exists for the item; sp_verify_claim
   additionally runs inside a transaction with FOR UPDATE.

Q16. How does matching work?
A. sp_find_matches scores unclaimed / claim-pending found items in
   the same category: category 40 + same location 30 + found within
   7 days after the loss 20 + first-title-word overlap 10; rows with
   score >= 50 are stored in Matches; the report becomes 'matched'.

Q17. Why is the matching score >= 50?
A. Category alone is 40, so any same-category item cannot become a
   match by accident; it needs at least one more positive signal
   (e.g. the date window +20, or location +30) to reach 50+. It keeps
   obvious noise out.

Q18. Why is Matches INSERT IGNORE / UNIQUE (report_id, item_id)?
A. Re-running matching must not create duplicates: the UNIQUE pair
   constraint forbids duplicates and INSERT IGNORE skips existing
   pairs, so re-runs are idempotent.

Q19. What is a view and why have two?
A. A saved SELECT query usable like a table. v_open_found_items hides
   the category/location joins from the browse route;
   v_claim_details gives the admin queue its rows in one place.

Q20. What is the difference between INNER and LEFT JOIN here?
A. v_claim_details uses a LEFT JOIN on the linked report because not
   every claim links a report; a LEFT JOIN keeps those rows with
   report_title NULL where an INNER JOIN would drop them.

Q21. What is SQL injection and how do you prevent it?
A. Entering SQL through user input into a concatenated query. We
   prevent it with ? placeholders - the driver sends values and SQL
   text separately, so quotes in the input are data, not code.

Q22. How does the item go from unclaimed to claimed?
A. Only through claims. The claim-insert trigger sets claim_pending;
   verifying a claim sets claimed; if a claim is rejected and no
   pending claims remain, back to unclaimed.

Q23. What is the AuditLog and who writes it?
A. A table written ONLY by the triggers in the MySQL version (INSERT
   and STATUS_CHANGE rows). Nobody writes to it from the app - that
   is the point: the history is database-guaranteed. On TiDB the app
   writes it explicitly.

Q24. Why does the frontend only call lib/api.js and not the database?
A. Separation of concerns: pages never touch SQL, so switching a
   route from mock to real SQL changes nothing in the UI; and no page
   can run an unparameterized query by accident.

Q25. What are ENUMs and why use them for status?
A. A column restricted to a fixed list of strings. Statuses are a
   small controlled vocabulary - ENUM keeps invalid values out of the
   database itself.

Q26. How would you show two claims competing for the same item?
A. Seed item 3 has two pending claims (6 and 7). Verifying claim 6 in
   the admin queue rejects claim 7 automatically with the note
   "Another claim was verified for this item".

Q27. What are the limitations of the matching?
A. It is rule-based (category, location, date window, one title
   word). No fuzzy search, no synonyms, no images or machine
   learning - a lost "iPhone 15" that shares neither the first word
   nor the exact dates can still be missed.

Q28. Why bcrypt and not plain passwords or MD5?
A. bcrypt is a slow, salted, adaptive one-way hash designed exactly
   for passwords; plain text is a data breach waiting to happen, and
   MD5/SHA are too fast to crack.

Q29. Why is the session cookie httpOnly?
A. Because JavaScript (document.cookie) cannot read httpOnly cookies,
   so an XSS bug cannot steal the session.

Q30. What is AUTO_INCREMENT and why not generate ids in the app?
A. The database assigns the next number per insert. Two concurrent
   inserts cannot collide, and the id exists only after the insert
   anyway (that is why the audit triggers are AFTER triggers).

THE NEW BATCH (after the TiDB split):

Q31. Why did you make a TiDB version of the SQL?
A. The app is meant to be hosted in the cloud (Vercel) with a cloud
   database. TiDB's free Starter tier fits a student project, and it
   is MySQL-compatible - tables, foreign keys, CHECKs, ENUMs and
   views all work unchanged - but it does not support triggers or
   stored procedures, so we split the SQL: sql/mysql/ keeps them for
   the local viva run, sql/tidb/ documents every rule they enforced
   as plain SQL for the app to execute (sql/tidb/APP_LOGIC.md).

Q32. What is lost when the triggers and procedures are gone?
A. Automaticity. On MySQL the rules fire no matter who inserts the
   row; on TiDB the application is trusted to run the equivalent
   statements. Concretely: audit rows can be forgotten, status flips
   can be skipped, future dates / double claims / self-claims are
   only blocked because OUR route checks them. The same DB-level
   constraints (FK, UNIQUE, CHECK, ENUM) still protect the data.

Q33. How are the rules enforced now?
A. In the route handlers, inside transactions, following
   APP_LOGIC.md: check-then-act with SELECT ... FOR UPDATE under
   row lock, then the INSERT/UPDATEs, then COMMIT; failures become
   HTTP 409 with the same messages the triggers used to raise.

Q34. How do you keep atomicity without the stored procedure?
A. The route handler opens one transaction itself:
   pool.getConnection(), beginTransaction(), try { statements },
   commit(); on any error rollback() and re-raise to send 409. The
   atomic guarantee comes from the transaction, not from where the
   code lives.

Q35. What could go wrong with two admins verifying at once?
A. Say admin A and admin B both open claim X. On MySQL: whoever's
   UPDATE lands first wins; the second one's BEFORE UPDATE trigger
   fails ('This claim has already been reviewed') - and inside
   sp_verify_claim the SELECT ... FOR UPDATE serialises them. On
   TiDB: the flattened script does the same FOR UPDATE first, and a
   second transaction blocks until the first commits, then reads the
   row as no longer pending and aborts. If the code SKIPPED the
   FOR UPDATE / didn't keep the transaction, both could pass the
   "status = pending" check and double-verify - that is the danger
   of moving the rule into the app.

Q36. Which version do you demo in the viva, and why?
A. The local MySQL version (sql/mysql/). The project's heart is the
   triggers, procedure and audit automation; that only visibly works
   there. The TiDB version is the honest answer to "would this run in
   production?" - same schema and data, rules moved to the app, and
   the fact we documented the equivalence is itself a talking point.

Q37. What is TiDB and why is it MySQL-compatible but not identical?
A. TiDB is an open-source distributed NewSQL database that speaks the
   MySQL protocol and supports most MySQL syntax. A distributed
   design makes triggers/procedures hard to serve, so TiDB does not
   offer them; transactions behave like MySQL's (it uses pessimistic
   row locks), AUTO_INCREMENT ids may skip, and TiDB Cloud forces
   TLS and keeps foreign_key_checks permanently enabled.

Q38. Your seed sanity check expects Matches 28 - why not 27?
A. Because that is what the scoring formula genuinely produces for
   the 20 reports against all 20 items: 18 reports get at least one
   match. Report 10 ("Bike keys", lost 15 days ago) alone scores two
   - item 20 (Library, within the window, first word "bike" matches,
   100) and item 4 (different location but within the date window,
   60). The mock store computes the same 28 rows with the same
   formula, and both were verified.

17. GLOSSARY
=====================================================================

  3NF (third normal form)  a table shape where no non-key column
              depends on another non-key column; removes update,
              insert and delete anomalies.
  ACID        Atomicity, Consistency, Isolation, Durability - the four
              guarantees of a transaction.
  App Router  Next.js' routing: a folder tree under app/ where each
              page.js is a page and each route.js is an endpoint.
  AUTO_INCREMENT  MySQL feature: assigns the next integer to a
              primary key automatically on insert.
  bcrypt      password hashing algorithm: slow and salted by design.
  CHECK       constraint with a condition every row must satisfy.
  claim       a user's statement, with proof, that a found item is
              theirs; reviewed by an admin.
  client component ("use client")  React component that runs in the
              browser and can use state/handlers.
  cookie (httpOnly)  a browser-stored value that HTTP requests send
              automatically; httpOnly keeps it away from scripts.
  CURDATE()   MySQL function: today's date (drives relative seed
              dates and the future-date triggers).
  data-bs-theme  Bootstrap 5.3's attribute for its built-in light /
              dark colour modes; set on <html> by ThemeToggle.
  ENUM        column type limited to a fixed list of string values.
  Exit handler  procedure code that runs on an SQL error (we use it
              to ROLLBACK and RESIGNAL).
  foreign key (FK)  column whose value must exist in another table's
              primary key.
  handover    the recorded moment an item was physically returned.
  httpOnly    cookie flag: JS cannot read or change the cookie.
  hot reload  Next.js dev feature: edited files apply without a full
              restart (the mock store survives it via globalThis).
  http status 400 / 401 / 403 / 404 / 409  bad request / not logged
              in / not allowed / not found / conflict.
  INSERT IGNORE  insert but silently skip rows that violate a UNIQUE
              key instead of failing.
  junction table  a table that turns a many-to-many relationship into
              pairs (our Matches (report_id, item_id)).
  LAST_INSERT_ID()  MySQL function: the AUTO_INCREMENT value of the
              last row the connection inserted (used by the app to
              replace trigger access to NEW.x).
  localStorage  browser key-value storage; keeps the theme choice.
  LOCATE / SUBSTRING_INDEX  MySQL string functions used to compare
              the first word of a title.
  match score  number 0..100 computed from category, location, date
              window and title word overlap.
  mock store  lib/mock-store.js - in-memory fake DB that mirrors the
              seed, used while the app is mock-first.
  MySQL 8     the local relational database (all features used).
  mysql2      the JavaScript driver library for MySQL / TiDB.
  NewSQL      a modern distributed SQL database family (TiDB).
  NOT NULL    column constraint: a value is mandatory.
  ORM         object-relational mapper; wraps SQL behind objects. Not
              used here deliberately (raw SQL is the point).
  pessimistic transaction  transactions that LOCK rows on read
              (SELECT ... FOR UPDATE) instead of retrying on write
              conflict; TiDB supports this mode, which the flattened
              verify script relies on.
  primary key (PK)  the column (or set) that uniquely identifies a
              row.
  procedure   a saved SQL program invoked with CALL.
  ? placeholder  a parameter marker in SQL text; the driver sends
              values separately, preventing injection.
  RESIGNAL    re-raises the caught error after a handler so the
              caller sees the real cause.
  RESTRICT    ON DELETE action that refuses deleting a parent that
              still has children.
