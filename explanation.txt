 0. HOW TO READ THIS DOCUMENT
================================================================================

This is the narrative companion to the codebase. Every page, route file,
table, trigger, procedure and view has an entry here. Code excerpts are
short on purpose - open the referenced file alongside this document; the
doc tells you what every piece is FOR and what breaks without it.

Reading order for a grader pressed for time:
  Section 4 (schema walkthrough) -> Section 5 (concepts survey, incl. the
  ACID transaction) -> Section 4.14 (sp_verify_claim). Those three cover
  the DBMS syllabus end-to-end.

One idea runs through the whole project: the DATABASE is the product.
The frontend exists so the examiner can SEE the database working - every
screen is a query, every button is a transaction, and the mock layer is a
faithful, runnable twin of the SQL so the demo works with or without a
server attached.


================================================================================
 1. SYSTEM OVERVIEW & ARCHITECTURE
================================================================================

Stack
-----
  Next.js 16 (App Router)   - frontend AND backend in one deployable app
  Bun 1.4                   - runtime + package manager (bun.lock committed)
  React 19                  - client components, hooks only (no TS)
  Bootstrap 5.3.3           - styling, loaded as CSS from the CDN only
                              (no Bootstrap JS anywhere; light/dark modes via
                              data-bs-theme)
  Schibsted Grotesk         - Google Font, loaded in the root layout
  MySQL 8 / TiDB Cloud      - database (canonical scripts target MySQL 8)
  mysql2 (promise API)      - driver, connection pool, prepared statements
                              (the real-mode swap; not wired yet)
  Vercel                    - deployment target

Architecture in one picture
---------------------------

    Browser (React 19 client components)
       |  fetch (credentials: same-origin)
       v
    Next.js route handlers  (app/api/**/route.js on Vercel)
       |-- lib/mock-auth.js   -> session cookie check (401/403 helpers)
       |-- lib/mock-store.js  -> business rules = the trigger/procedure
       |                         twins, returning { error, status } or data
       v
    (mock phase)  in-memory store on globalThis, seeded exactly like
                  sql/seed.sql - dates computed relative to today
    (real phase)  mysql2 pool (lib/db.js, to be added) -> MySQL 8 / TiDB

Why mock-first
--------------
The PRD mandated it: the whole UI ships before a server exists, and every
API route is a ~20-line file whose BODY can be swapped for real SQL one
route at a time. The response shape (same snake_case fields) and the same
error codes (400 validation / 401 anonymous / 403 non-admin / 404 missing /
409 trigger conflict) are fixed by contract, so pages never change when a
route goes real.

Roles and what they unlock
--------------------------
  admin        - everything, plus the claim queue, stats and audit log
  user/student - report lost items, browse and claim found items, track
                 own reports and claims

Both roles share one `users` table; the role column is an ENUM and every
admin route answers 403 "Admin only" for non-admins.

Request lifecycle (one claim, end to end)
-----------------------------------------
 1. Student opens /browse, the page fetches GET /api/found - the mock
    returns only status='unclaimed' items, shaped like the
    v_open_found_items view.
 2. Student opens /item/3, reads the detail, fills proof text and
    submits the claim form -> POST /api/claims.
 3. The route checks the session cookie, then createClaim() re-checks
    every rule of trg_claim_before_insert IN THE SAME ORDER the trigger
    does; any violation returns the trigger's exact message as a 409.
 4. On success the item flips unclaimed -> claim_pending and an audit row
    is written (trg_claim_after_insert), the response is { claim_id }.
 5. An admin opens /admin, sees the queue (rows shaped like
    v_claim_details), clicks Verify with a note -> POST
    /api/admin/claims/3/verify -> sp_verify_claim's three steps run
    (verify + reject other pendings + handover), all statuses propagate.

================================================================================
 3. BACKEND EXPLAINED - FUNCTION BY FUNCTION
================================================================================

The backend is 20 route files under app/api/ - each one is a thin shell
(check session, parse body, call one store function, map {error,status}
to an HTTP code) around lib/mock-store.js, which is where the logic lives.
The store is a faithful twin of the SQL layer: every function is annotated
with the trigger or procedure it mirrors, and seed replay produces the
same 57 audit rows the real triggers would.

3.1 The store itself (lib/mock-store.js)
-----------------------------------------
  createStore()       builds all 9 "tables" with AUTO_INCREMENT sequence
                      counters, then replays the seed exactly like
                      schema.sql + logic.sql + seed.sql: users/lookups,
                      lost+found inserts (writing the trg_*_after_insert
                      audit rows), runMatching(1..20) (the 20
                      CALL sp_find_matches), report 11 -> closed, the 9
                      claim inserts (claim_pending flips + audit), three
                      sp_verify_claim runs, one manual rejection.
                      Lives on globalThis so Next hot reloads do not wipe
                      the demo mid-presentation.

  runMatching(reportId)   the sp_find_matches twin, see 3.4.
  addAudit(...)           the audit-trigger twin: one row into auditLog.
  getDb()                 lazy singleton accessor.

3.2 Auth routes
---------------
  POST /api/register  server-side validation (the browser checks too, but
                      never trust it): name, email shape, phone digits,
                      password length. createUser() rejects duplicate
                      email with 409. Session cookie is set on success.
  POST /api/login     getUserByEmail + checkPassword; "Invalid email or
                      password" on failure (same message for both - never
                      reveal which half was wrong). Mock compares plain
                      text; real mode uses bcryptjs against the hash.
  POST /api/logout    clears the cookie.
  GET  /api/me        who am I, or 401.

3.3 Reference data
------------------
  GET /api/categories  the 9 lookup rows (dropdown feeds).
  GET /api/locations   the 8 lookup rows.

3.4 Lost reports
----------------
  POST /api/lost           createLostReport(): validates title >= 3 chars
                           (chk_lost_title), known category/location (the
                           FKs), date shape, then trg_lost_before_insert's
                           rule - no future dates. Insert, audit row
                           (trg_lost_after_insert), then matching runs
                           immediately (PRD FR4): a new report meets the
                           existing found items in the same tick.
  GET  /api/lost/mine      my reports newest first, each with match_count.
  GET  /api/lost/[id]/matches   my matches for one report, best first -
                           the UI of required query 1.
  POST /api/lost/[id]/rematch   re-run matching for my report - the mock
                           of CALL sp_find_matches(report_id); returns
                           { matches_created } exactly like the procedure.
  PATCH /api/lost/[id]     close MY report (403 if not mine); only an
                           open/matched report may close.

  runMatching(reportId)    THE SCORING, identical to the procedure:
                             +40  same category (hard filter, not a bonus
                                  - "a phone is never a match for a wallet")
                             +30  same location
                             +20  item found within 7 days AFTER the loss
                             +10  report title's first word (>= 3 chars)
                                  appears in the item title (case-insensitive)
                             threshold: >= 50 to become a Matches row;
                             existing pairs skipped (the UNIQUE(report_id,
                             item_id) / INSERT IGNORE semantics); if any
                             match was created, an 'open' report flips to
                             'matched'.

3.5 Found items
---------------
  POST /api/found          createFoundItem(): same validation family
                           (chk_found_title, FKs, trg_found_before_insert
                           no-future-date), insert, audit row.
  GET  /api/found?...      listFoundItems(): ONLY status='unclaimed' rows
                           (the view's WHERE), filterable by category,
                           location, date range and keyword in
                           title/description, newest first - required
                           query 2 as an endpoint.
  GET  /api/found/[id]     one item's full record.

3.6 Claims (the trigger heart)
------------------------------
  POST /api/claims         createClaim() re-checks trg_claim_before_insert
                           IN THE TRIGGER'S ORDER, returning its exact
                           messages as 409:
                             item claimed/disposed      -> "This item is no
                                longer available to claim"
                             finder claiming own item   -> "You cannot
                                claim an item you found yourself"
                             duplicate pending claim    -> "You already
                                have a pending claim on this item"
                             linked report not mine     -> "The linked
                                lost report does not belong to you"
                           then insert, trg_claim_after_insert (item
                           unclaimed -> claim_pending), audit row.
  GET  /api/claims/mine    my claims newest first with admin notes.

3.7 Admin
---------
  GET  /api/admin/claims?status=    the queue, rows shaped exactly like
                           the v_claim_details view (claimant name/email,
                           item title, linked report title, proof).
  POST /api/admin/claims/[id]/verify
                           verifyClaim(): 404 unknown, 409 already
                           reviewed, 409 if another claim is already
                           verified on the item (trg_claim_before_update),
                           then verifyClaimInStore runs sp_verify_claim's
                           three steps:
                             1. claim -> verified + reviewed_by + note +
                                reviewed_at; audit STATUS_CHANGE;
                                item -> 'claimed'; linked report ->
                                'resolved' (trg_claim_after_update).
                             2. every OTHER pending claim on the item ->
                                rejected with "Another claim was verified
                                for this item" (+ audit).
                             3. one Handovers row is recorded.
  POST /api/admin/claims/[id]/reject
                           rejectClaim(): reject with note; if no pending
                           claim remains on the item, the item goes back
                           to 'unclaimed' (the trigger's rejected branch).
  GET  /api/admin/stats    getAdminStats(): status counters; hotspots =
                           lost reports per location (required query 4);
                           category-wise open vs resolved (query 6);
                           stale_items = unclaimed over 30 days with
                           day arithmetic (query 5). Admin only.
  GET  /api/admin/audit    latest 100 audit rows, newest first - the
                           trigger-written trail. Admin only.


================================================================================
 4. sql/ - THE DATABASE, EXPLAINED EXHAUSTIVELY
================================================================================

The sql/ folder ships in two flavours:

  sql/mysql/  schema.sql + logic.sql + seed.sql + reset.sql
              - the CANONICAL version for local MySQL 8 (also tested on
                MariaDB 11). Full triggers, procedures, views.
  sql/tidb/   00_create_database.sql .. 04_sanity_check.sql + APP_LOGIC.md
              - the TiDB Cloud version: identical tables/views/data, but
                everything triggers and procedures did is written out as
                plain SQL (see Section 6).

4.0 Conventions (both versions)
-------------------------------
  utf8mb4 everywhere - true Unicode. ENGINE=InnoDB - transactions and row
  locks (parsed and ignored by TiDB, honored by MySQL).
  Surrogate INT AUTO_INCREMENT PKs on every table: no natural key is safe
  (titles get edited, emails change); ids never change.

4.1 users
---------
  user_id       PK AUTO_INCREMENT
  name          VARCHAR(100) NOT NULL
  email         VARCHAR(120) NOT NULL UNIQUE - the login name; UNIQUE
                doubles as the lookup index and blocks double accounts
  phone         VARCHAR(15) - kept VARCHAR: phones carry '+', spaces and
                leading zeros; they are not numbers you compute with
  role          ENUM('user','admin') NOT NULL DEFAULT 'user' - a closed
                domain of exactly two roles
  password_hash VARCHAR(100) NOT NULL - bcrypt output (~60 chars)
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP - free
                provenance on every row

4.2 categories / 4.3 locations        THE LOOKUP TABLES
  category_id / location_id PK, name UNIQUE (UNIQUE doubles as the list
  index; two "Library" rows would poison every FK choice), plus the
  optional building VARCHAR(80). These tables are 3NF in action: the big
  tables store cheap integer ids, and the spelling of "Laptop/Charger"
  lives in exactly ONE place.

4.4 lost_reports                       THE "PLEA" TABLE
  report_id PK
  user_id      FK -> users ON DELETE RESTRICT - a report is a user's
               record; deleting the user out from under it is a data-loss
               bug, so RESTRICT forces deliberate disentangling
  category_id  FK -> categories ON DELETE RESTRICT
  location_id  FK -> locations ON DELETE RESTRICT
  title        VARCHAR(120) NOT NULL + CHECK (CHAR_LENGTH(title) >= 3)
               - domain rule straight in the DDL
  description  TEXT NULLable
  date_lost    DATE NOT NULL
  status       ENUM('open','matched','resolved','closed')
               NOT NULL DEFAULT 'open' - the status MACHINE: open ->
               matched (a match was created) -> resolved (a claim was
               verified), or open -> closed (the owner gave up)
  created_at   DEFAULT CURRENT_TIMESTAMP

4.5 found_items                        THE "INVENTORY" TABLE
  item_id PK; finder_id FK -> users RESTRICT (same reasoning);
  category_id/location_id FKs RESTRICT; title + the same CHECK;
  description TEXT; stored_at VARCHAR(100) - where the physical item sits
  (help desk, warden office) - the field that turns a database row into a
  real object someone must hand over;
  date_found DATE NOT NULL;
  status ENUM('unclaimed','claim_pending','claimed','disposed')
       NOT NULL DEFAULT 'unclaimed' - the mirror machine, driven almost
       entirely by triggers: unclaimed -> claim_pending (a claim arrived)
       -> claimed (claim verified) or back to unclaimed (all claims
       rejected); disposed is the admin's manual "never returned" state.

4.6 matches                            THE SUGGESTION TABLE
  match_id PK; report_id FK -> lost_reports ON DELETE CASCADE; item_id
  FK -> found_items ON DELETE CASCADE (a match is a PAIRING: it has no
  meaning if either side disappears, so it dies with them);
  score INT NOT NULL CHECK (score BETWEEN 0 AND 100);
  created_at.
  UNIQUE KEY uq_match_pair (report_id, item_id)
       THE signature constraint of this table: the same pairing can never
       be suggested twice. It is what makes the procedure's INSERT IGNORE
       idempotent - re-running matching is always safe.

4.7 claims                             THE TRUST TABLE
  claim_id PK; item_id FK -> found_items RESTRICT (claims are evidence,
  they outlive the item's availability); claimant_id FK -> users RESTRICT;
  report_id FK -> lost_reports ON DELETE SET NULL NULLable - the OPTIONAL
  link "I also filed a report for this"; deleting that report must not
  delete the claim, it must only detach the link - SET NULL is the exact
  referential action for "optional link";
  proof_text TEXT NOT NULL - the claimant's written evidence;
  status ENUM('pending','verified','rejected') NOT NULL DEFAULT 'pending';
  reviewed_by FK -> users ON DELETE SET NULL - who reviewed it; if that
  admin account ever vanishes, the review survives with a NULL reviewer;
  admin_note VARCHAR(255) - the reason, shown back to the claimant;
  created_at / reviewed_at - the two timestamps the "pending > 3 days"
  and average-resolution queries are built from.

4.8 handovers                          THE RECEIPT TABLE
  handover_id PK; claim_id FK + UNIQUE -> claims RESTRICT - the UNIQUE
  converts 1:N into 1:1: exactly one handover per verified claim, no
  double handovers; handed_by FK -> users RESTRICT; handed_at DATETIME
  DEFAULT CURRENT_TIMESTAMP; remarks VARCHAR(255). A handover row is the
  physical "item left the office" event.

4.9 audit_log                          THE BLACK BOX
  log_id PK; table_name VARCHAR(30); action VARCHAR(30); record_id INT;
  details VARCHAR(255); performed_at DEFAULT CURRENT_TIMESTAMP.
  Written ONLY by triggers (or their TiDB app-twins). No FKs BY DESIGN -
  a log must survive even if the referenced row is deleted; it records
  INSERT / STATUS_CHANGE / handover events with the exact same sentence
  the UI shows.

4.10 triggers - clause by clause (sql/mysql/logic.sql)
------------------------------------------------------
  trg_lost_before_insert / trg_found_before_insert   BEFORE INSERT
    IF NEW.date_lost > CURDATE() THEN SIGNAL SQLSTATE '45000' ...
    BEFORE gives the app the vocabulary of rejection BEFORE the row
    exists. SIGNAL raises a catchable user-defined error. Why a trigger
    and not a CHECK? MySQL 8 CHECK constraints cannot call
    nondeterministic functions like CURDATE() - a case study in where
    each constraint mechanism belongs.

  trg_lost_after_insert / trg_found_after_insert     AFTER INSERT
    One sentence into audit_log per new row. AFTER, because the audit
    must reflect a row that actually landed.

  trg_claim_before_insert   BEFORE INSERT claims - THE BUSINESS RULES,
    in enforcement order:
      1. item status IN ('claimed','disposed')   -> reject
      2. finder_id = claimant_id                 -> reject (no self-
         claiming, found it yourself)
      3. EXISTS another pending claim by the same user on the same item
                                                 -> reject (no spam)
      4. report_id given but its owner <> claimant -> reject (you cannot
         anchor your claim to someone else's report)
    Four rules the schema alone cannot express (they need reads) - this
    is exactly the workload triggers exist for.

  trg_claim_after_insert    AFTER INSERT
    item unclaimed -> claim_pending (guarded WHERE status='unclaimed' so
    a second claim cannot undo 'claimed'), + audit row.

  trg_claim_before_update   BEFORE UPDATE
    - OLD.status <> 'pending' AND NEW.status <> OLD.status -> reject:
      a reviewed claim can never be re-reviewed (immutability of verdicts)
    - NEW.status='verified' while another verified claim exists on the
      item -> reject: ONE verified claim per item
    - first review stamps reviewed_at = NOW() automatically.

  trg_claim_after_update    AFTER UPDATE (only when status changed)
    verified: item -> 'claimed'; linked report -> 'resolved'
    rejected: if NO other pending claim remains on the item, item
              claim_pending -> 'unclaimed'
    + one STATUS_CHANGE audit row. This trigger is the sync engine that
    keeps three tables consistent from one UPDATE.

  trg_handover_before_insert   BEFORE INSERT
    the claim must already be 'verified' - you cannot hand over an item
    whose claim is still pending; plus audit row on AFTER INSERT.

4.11 procedures
---------------
  sp_find_matches(IN p_report_id)
    DECLARE v_created INT DEFAULT 0;
    INSERT IGNORE INTO matches (report_id, item_id, score)
      SELECT ... (CASE) + (CASE) + (CASE) + (CASE) ... AS score
      FROM lost_reports r JOIN found_items f
        ON f.status IN ('unclaimed','claim_pending')
      WHERE r.report_id = p_report_id
        AND r.status IN ('open','matched')
        AND f.category_id = r.category_id
      (score >= 50 in the outer WHERE);
    SET v_created = ROW_COUNT();
    IF v_created > 0 THEN UPDATE lost_reports SET status='matched'
      WHERE report_id = p_report_id AND status='open'; END IF;
    SELECT v_created AS matches_created;
    The scoring CASEs are the four weights of 3.4. INSERT IGNORE + the
    UNIQUE pair makes reruns idempotent; ROW_COUNT() counts only NEW
    pairs; the procedure RETURNS its result as a one-row result set.

  sp_verify_claim(IN p_claim_id, p_admin_id, p_note, p_remarks)
    THE TRANSACTION - ACID made concrete (see 5.4):
      DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN ROLLBACK; RESIGNAL; END;
      admin check (role='admin') else SIGNAL;
      START TRANSACTION;
      SELECT item_id INTO v_item FROM claims
        WHERE claim_id=? AND status='pending' FOR UPDATE;
      IF v_item IS NULL THEN SIGNAL 'Claim not found or already reviewed';
      UPDATE claims SET status='verified' ... ;     (fires the triggers)
      UPDATE claims SET status='rejected',
             admin_note='Another claim was verified for this item'
             WHERE item_id=v_item AND claim_id<>p_claim_id
               AND status='pending';
      INSERT INTO handovers ...;
      COMMIT;
    Every step succeeds or NONE does: a half-verified claim with no
    handover is impossible. FOR UPDATE row-locks the claim so two admins
    clicking Verify at once serialize: the second one re-reads the status
    after the first commits and gets the friendly 409.

4.12 views
----------
  v_open_found_items   unclaimed items flattened with category + location
                       names (the Browse screen is this view + filters).
  v_claim_details      the admin queue: claim + claimant + item + linked
                       report in one shape, so the UI never writes a JOIN.
  Views = logical data independence: consumers see stable shapes while
  the underlying joins evolve.

4.13 seed (sql/mysql/seed.sql) - what each block demonstrates

================================================================================
 5. RDBMS CONCEPTS USED - A SURVEY
================================================================================

Normalization (1NF -> 3NF)
--------------------------
  1NF: atomic cells - a report is one row with one title, one date, one
       category; no repeating "keyword1..keyword3" columns anywhere.
  2NF: every non-key attribute depends on the WHOLE key - each fact
       (user, category, location, report, item, claim, handover) is its
       own table; nothing rides on part of a composite key (the only
       composite is uq_match_pair, which is a constraint, not a key).
  3NF: no transitive chains - the category NAME is never stored on a
       report (only category_id, name lives once in categories); the
       claimant's NAME is never stored on a claim (only claimant_id).
       Change "Academic Block" to "Academic Block 2" in ONE row and every
       report updates with it - no update anomalies.

Integrity - the three flavors
-----------------------------
  Entity:      PKs everywhere; UNIQUE email on users, UNIQUE name on both
               lookups, UNIQUE (report_id, item_id) on matches, UNIQUE
               claim_id on handovers.
  Referential: nine FKs with three different ON DELETE policies, each
               chosen by MEANING - RESTRICT where history must be
               protected (reports, items, claims), CASCADE where the
               child is meaningless alone (matches), SET NULL where the
               link is optional (claims.report_id, claims.reviewed_by).
  Domain:      ENUM status machines on users/lost_reports/found_items/
               claims; CHECK title >= 3 chars on both big tables, CHECK
               score BETWEEN 0 AND 100; NOT NULLs; DATE/DATETIME types;
               DEFAULT 'open'/'unclaimed'/'pending'.
  Plus the rules SQL constraints cannot express (they need reads or
  CURDATE()): no future dates, the four claim rules, one-verified-per-
  item, handover-only-after-verify - all trigger territory (Section 4.10).

Relationships & cardinality
---------------------------
  users 1:N lost_reports          users 1:N found_items (finder)
  categories 1:N both             locations 1:N both
  lost_reports 1:N matches        found_items 1:N matches
  found_items 1:N claims          users 1:N claims (claimant)
  lost_reports 0..1 claims (SET NULL optional link)
  claims 1:1 handovers (UNIQUE FK)
  users 0..1 claims-reviewed (reviewed_by SET NULL)

Transactions & concurrency (ACID)
---------------------------------
  Atomicity:    sp_verify_claim wraps verify + mass-reject + handover in
                one BEGIN...COMMIT with an EXIT HANDLER that ROLLBACKs and
                RESIGNALs. A crash between "verified" and "handover"
                leaves NO trace - the claim stays pending. The TiDB twin
                runs the identical steps in one route-level transaction.
  Consistency:  after every transaction the constraints + triggers (or
                their app twins) re-assert every invariant: statuses
                agree across three tables, exactly one verified claim per
                item, one handover per verified claim, audit trail
                complete.
  Isolation:    InnoDB default REPEATABLE READ + SELECT ... FOR UPDATE.
                Two admins verifying the same claim race on the same
                claim row: tx 2 blocks inside FOR UPDATE until tx 1
                commits, then finds status <> 'pending' and raises
                "Claim not found or already reviewed" -> 409. No lost
                updates, no double handovers - the lock is only the gate;
                the UNIQUE + status machine are the real guarantee.
  Durability:   COMMIT + the engine's redo log (MySQL InnoDB / TiDB
                Raft-majority replication). Nothing app-level to do.

Deliberate design choices (the "why" answers)
---------------------------------------------
  Surrogate keys everywhere        - natural keys rot; ids never change.
  VARCHAR phone                    - phones are text, not arithmetic.
  DECIMAL-free zone, but DATE for  dates: DATE math (the 7-day window,
                                   the 30-day staleness) stays in SQL.
  matches as a STORED table        - suggestions are materialized so the
                                   "my matches" screen is a single indexed
                                   read, and rematch is cheap (INSERT
                                   IGNORE). The score is frozen at match
                                   time - the suggestion must not silently
                                   change under the user.
  audit_log without FKs            - logs must survive the referenced row.
  status machines as ENUMs         - closed domains, indexable, self-
                                   documenting in SHOW CREATE TABLE.
  report_id SET NULL               - detach, never delete, history.


================================================================================
 6. DEPLOYMENT DIVERGENCE NOTE (CANONICAL MYSQL VS TIDB CLOUD)
================================================================================

sql/mysql/ is complete MySQL 8: triggers, procedures, views. The hosted
demo runs on TiDB Cloud (free tier), which does not implement
CREATE TRIGGER / CREATE PROCEDURE / CREATE FUNCTION at all. So sql/tidb/
loads tables + lookup rows + views (all fully supported - FKs enforced,
CHECKs enforced, ENUMs, views) and every trigger/procedure behavior is
written out as plain SQL in sql/tidb/03_seed.sql, and lives in the
application layer for runtime writes - the mock-store functions in
Section 3 are line-for-line the trigger bodies, and sql/tidb/APP_LOGIC.md
is the ready-to-run SQL translation for the mysql2 swap:

  trg_lost/found_before_insert  -> date guard in createLostReport /
                                   createFoundItem (400 on future dates)
  trg_lost/found_after_insert   -> addAudit(...) after every insert
  trg_claim_before_insert       -> the four 409 rules in createClaim
  trg_claim_after_insert        -> claim_pending flip + audit row
  trg_claim_before_update       -> "already reviewed" / "one verified
                                   per item" guards in verifyClaim
  trg_claim_after_update        -> claimed/resolved/unclaimed syncs in
                                   verifyClaimInStore / rejectClaimInStore
  trg_handover_before_insert    -> verified-only guard before the insert
  sp_find_matches               -> runMatching() at runtime; the
                                   INSERT ... SELECT with identical scoring
                                   in sql/tidb/03_seed.sql for the seed
  sp_verify_claim               -> verifyClaimInStore(): verify + reject
                                   other pendings + handover, one
                                   transaction when on real SQL

On a real MySQL 8 host NOTHING changes: sql/mysql/reset.sql activates the
trigger/procedure layer again and the same app keeps working - the
app-side logic is idempotent-shaped (guards + guarded UPDATEs), not
duplicative.

Load order on TiDB Cloud (from the project root):
    mysql --host <HOST> --port 4000 -u <USER> -p \
          --ssl-mode=VERIFY_IDENTITY < sql/tidb/00_create_database.sql
    (then 01_schema.sql, 02_views.sql, 03_seed.sql, 04_sanity_check.sql)

Load order on local MySQL 8:
    mysql -u root -p < sql/mysql/reset.sql
